A secret backend decides what manifest a `Secret.define` member turns into when bound. `Environment.bind` and `Secret.bind` never touch plaintext themselves; they hand the member's name, namespace, and key list to the backend's `emit`, along with an optional `SecretSource` that can resolve the values.

## The interface

```ts
interface SecretBackend<N extends string, K extends string, RequiresSource extends boolean = boolean, Out = unknown> {
  readonly _tag: "Sops" | "Sops.passthrough" | "SealedSecrets" | "ExternalSecrets" | "NativeSecret"
  readonly requiresSource: RequiresSource
  readonly emit: (input: BackendEmitInput<N, K, RequiresSource>) => Manifest.Manifest<Out>
}
```

`BackendEmitInput` carries `name`, `namespace`, `keys`, optional `labels` / `annotations`, and `source`, whose type is `SecretSource<K>` when `RequiresSource` is `true` and `SecretSource<K> | undefined` otherwise.

`RequiresSource` lives in the type because it changes the shape of the `secrets` entry you must write in `Environment.bind`: a `true` backend makes `source` a required property, a `false` backend makes it optional. Forgetting the source for a backend that encrypts at render time is a compile error rather than a render-time `RenderError`. The runtime still checks (`bindSecret` emits a failing manifest with `backend "<tag>" requires a source but none was provided`) because the parameter is erased inside the generic bind code.

A `SecretSource<K>` is `{ keys, resolve: Effect<Record<K, Redacted<string>>, SecretSourceError, R> }`. `@konfig.ts/env` ships `SecretSource.fromConfig({ keys, envName? })` (reads env vars), `SecretSource.literal({ data })`, and `SecretSource.fromCommand({ keys, run })` (one subprocess per key, empty output is an error). `@konfig.ts/sops` adds `Sops.source({ file, keys, extract? })`, which decrypts a sops file once and plucks the keys.

## Backends

| Backend | Package | `requiresSource` | Emits |
| --- | --- | --- | --- |
| `NativeSecret.backend(opts?)` | `@konfig.ts/k8s` | `true` | `v1/Secret` with `stringData` |
| `Sops.backend({ recipients, type? })` | `@konfig.ts/sops` | `true` | `SopsSecret` (encrypted at render time) |
| `Sops.passthrough({ file })` | `@konfig.ts/sops` | `false` | `SopsSecret` read from disk |
| `SealedSecrets.backend({ scope?, certPath? })` | `@konfig.ts/sealed-secrets` | `true` | `SealedSecret` |
| `ExternalSecrets.backend({ secretStoreRef, refreshInterval?, remoteRef?, target? })` | `@konfig.ts/external-secrets` | `false` | `ExternalSecret` |

### NativeSecret

Writes the resolved plaintext into a `stringData` Secret. Options: `type`, `immutable`, `silenceWarning`. Every render logs a warning that a plaintext Secret is being written to disk unless `silenceWarning: true`; intended for local clusters and tests.

### Sops

`Sops.backend` resolves the source, serialises a plain `SopsSecret` CR (`isindir.github.com/v1alpha3`, one `secretTemplates` entry with `stringData`), pipes it through `sops --encrypt` for the given `recipients` (`age`, `kms`, `gcpKms`, `azureKv`, `pgp`, each validated against its key format), then decodes the output. `Sops.passthrough` skips encryption: it reads an already-encrypted file from disk. If the file's `metadata.name` / `metadata.namespace` or template name differ from the bound member, it restamps them, which is only allowed when the file's `sops.mac_only_encrypted` is `true` (otherwise the MAC covers those fields and the render fails). It works offline and needs no `sops` binary.

Both paths share a fail-closed verification step: the document must decode against the `SopsSecret` schema (including a top-level `sops` block), and every `stringData` / `data` value must carry the `ENC[` marker (when the file sets `encrypted_regex`, only the keys it matches must). A plaintext value fails with a `RenderError` whose message says it is refusing to emit because the value for that key is not sops-encrypted.

### Sealed Secrets

`SealedSecrets.backend` resolves the source, builds a plain `v1/Secret` YAML, and runs `kubeseal --cert <path> --scope <scope> --format yaml`. The certificate path comes from `certPath` or `$KUBESEAL_CERT`; when neither is set the render fails with `KubesealCertMissing` (wrapped in a `RenderError` with the message `cert missing`). `scope` defaults to `"strict"`; `"namespace-wide"` and `"cluster-wide"` are accepted. Output is decoded against the `SealedSecret` schema; a non-YAML result is `KubesealParseError`.

### External Secrets

`ExternalSecrets.backend` needs no plaintext at all: it emits an `external-secrets.io/v1` `ExternalSecret` whose `data` maps each key to `{ secretKey: key, remoteRef: remoteRef(key) }`. The default `remoteRef` is `{ key }`; pass `remoteRef: (key) => ({ key: "prod/db", property: key })` to map onto your store's layout. `secretStoreRef.kind` defaults to `SecretStore`. Because `requiresSource` is `false`, a member bound this way has no `values` / `layer` unless you also pass a `source` for render-time use.

<Aside type="note" title="Choosing">
Use `Sops.passthrough` or `ExternalSecrets` when the CI runner should never see plaintext. Use `Sops.backend`, `SealedSecrets`, or `NativeSecret` when the render environment holds the values (for example `SecretSource.fromConfig` on a developer machine or a sealed CI job) and you want the encrypted artifact generated on the fly.
</Aside>
