`@konfig.ts/sops` lowers a `Secret.define` contract to a `SopsSecret` custom resource that the in-cluster [sops-secrets-operator](https://github.com/isindir/sops-secrets-operator) decrypts into a native `Secret`. Ciphertext is the only thing that ever reaches the rendered manifests. This guide follows the example project's `db-creds` secret from contract to rotation.

## Steps

<Steps>

1. **Define the contract.** `Secret.define` names the Kubernetes Secret, its namespace, and a map from key to env var name. The same value is imported by the workload module (to bind) and by the app (to decode at runtime), so a rename moves both sides.

   <Snippet file="shared/env-contracts/src/secrets.ts" startAt="export const dbCreds" endBefore="export const s3Creds" title="shared/env-contracts/src/secrets.ts" />

2. **Create the encrypted file.** The committed file is a complete `SopsSecret` CR encrypted with `sops`; only `stringData` (and `data`) values are ciphertext, `metadata` and the `sops:` block stay readable. Write the plaintext CR, then run `sops --encrypt --age <recipient> --encrypted-regex '^(data|stringData)$' --in-place infra/secrets/SopsSecret-db-creds.yaml`. The result looks like this (the example ships fake ciphertext so it renders offline):

   <Snippet file="infra/secrets/SopsSecret-db-creds.yaml" lang="yaml" title="infra/secrets/SopsSecret-db-creds.yaml" />

   `spec.secretTemplates[].name` must equal `metadata.name`, and both should equal the `name` in `Secret.define`; the keys under `stringData` must cover every key of the contract's `env` map.

3. **Install the operator** as its own Application at an early sync wave, so the CRD and controller exist before any `SopsSecret` is applied. The operator reads its age key from a Secret you create out of band (`sops-age` in the example).

   <Snippet file="infra/modules/sops-operator.ts" startAt="export const defineSopsOperator" title="infra/modules/sops-operator.ts" />

4. **Bind in the module.** `Environment.bind` takes the env contract and one backend per secret member. `Sops.passthrough({ file })` reads the encrypted file at render time and emits it as the manifest; `bound.manifests` carries the CRs and `bound.envVars` the `secretKeyRef` entries for the container.

   <Snippet file="infra/modules/api.ts" startAt="      const bound = Environment.bind" endBefore="      const apiContainer" title="infra/modules/api.ts" />

   For a single secret outside an env contract, `Secret.bind({ secret, backend })` does the same and returns `{ ref, envVars, manifest, refLayer }`; `image-pulls.ts` uses it for the registry credential.

5. **Render.** `konfig build prod` writes `SopsSecret-db-creds.yaml` into the `api` Application's directory. Argo CD applies it, the operator decrypts it in-cluster, and the pod's `DATABASE_URL` env var resolves from the resulting native `Secret`.

</Steps>

## passthrough versus backend + source

`Sops` exposes three functions:

| | `Sops.passthrough({ file })` | `Sops.backend({ recipients, type? })` + `Sops.source({ file, keys, extract? })` |
| --- | --- | --- |
| Needs `sops` binary at build | No | Yes (`sops --decrypt` then `sops --encrypt`) |
| Needs the private key at build | No | Yes, to decrypt the source |
| `source` in the bind | Optional (`requiresSource: false`) | Required by the type (`requiresSource: true`) |
| Output | The committed file, verified and restamped | A fresh `SopsSecret` re-encrypted to `recipients` |

Use `passthrough` when the file is already encrypted for the cluster and CI should not hold a decryption key. Use `backend` + `source` when the source of truth is encrypted for developers and CI re-encrypts to the cluster's recipient, or when the source is a different backend altogether (`Sops.source` yields `Redacted` values any `SecretBackend` can consume, for example sealed-secrets).

`recipients` accepts `age`, `kms`, `gcpKms`, `azureKv`, and `pgp` arrays. `type` sets `secretTemplates[].type` and defaults to `Opaque`.

Restamping: `passthrough` rewrites `metadata.namespace` and `name` to the bound values only when the file's `sops.mac_only_encrypted` is `true`. Otherwise the MAC covers those fields and konfig refuses to change them, so name the file's metadata to match the contract.

## Fail closed

Every emitted CR passes through the same pipeline: parse YAML, decode against the `SopsSecret` schema, then check that each value under `stringData` and `data` starts with `ENC[` (honouring `sops.encrypted_regex` when present). A value without the marker fails the render with a `RenderError` whose cause is `SopsUnencryptedValueError`, and nothing is written for that Application:

```text
Sops.passthrough(app/db-creds): refusing to emit, value for "password" is not sops-encrypted (missing ENC[ marker)
```

The same check runs on `sops --encrypt` output in `backend` mode, so a misconfigured `encrypted_regex` cannot produce a plaintext CR.

## Rotation

Rotating a value means re-encrypting the file (`sops --rotate` or edit and re-encrypt), committing, and rendering. The manifest changes, Argo CD applies it, and the operator updates the native `Secret`. Whether pods pick the change up depends on how you asked for it:

- `Workload.web({ reloader: "stakater" })` adds `reloader.stakater.com/auto: "true"` to the Deployment, so a running [Reloader](https://github.com/stakater/Reloader) restarts pods when the in-cluster `Secret` changes. `"stakater-strict"` adds the `match` annotation, and `{ secrets: [...], configMaps: [...] }` targets specific names. This is the option that works with `passthrough`, because konfig never sees the plaintext.
- `hashSecretValues({ values, salt })` from `@konfig.ts/k8s` produces a fingerprint of resolved values you can put in a pod annotation, so a re-render with new values changes the pod template and rolls the Deployment without a controller. It needs the plaintext at build time, so it pairs with `Sops.source` (or `Secret.bind({ source })`, which exposes a `values` service), not with `passthrough`.

<Aside type="caution" title="Do not commit plaintext">
The committed `SopsSecret-*.yaml` files are safe to publish only because their values are ciphertext. Keep the private age key out of the repository and out of `konfig build` unless you deliberately chose the `backend` mode.
</Aside>
